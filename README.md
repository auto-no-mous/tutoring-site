# tutoring-site (my-tutor.ru)

Платформа для репетиторов и учеников: каталог с поиском по предмету и цене,
запись на занятия (индивидуальные и групповые), домашние задания, чат,
уведомления на почту и в Telegram, отзывы и статистика, полноценная админка.

Список предметов и направлений подготовки настраивается администратором (не
зашит в код), поэтому сайт подходит для репетитора любого предмета, а не
только информатики, с которой начинался замысел. Подробное описание всей
функциональности по ролям (репетитор/ученик/администратор) — в
[`project_description.md`](./project_description.md); этот файл — про то, как
поднять сайт локально или на сервере.

**Стек:** FastAPI + SQLAlchemy (async) + Alembic + SQLite/PostgreSQL на
бэкенде; Vue 3 + Vite + TypeScript + Pinia + Tailwind на фронтенде. Подробнее
— раздел 9 [`project_description.md`](./project_description.md).

## Быстрый локальный запуск

```
.\run-local.ps1
```

Ставит зависимости, применяет миграции, поднимает backend и frontend каждый в
своём окне PowerShell и открывает сайт в браузере (http://127.0.0.1:5173).
Если зависимости уже установлены — `.\run-local.ps1 -SkipInstall` быстрее.
Остановить — закрыть открывшиеся окна или Ctrl+C в каждом.

Этого достаточно, чтобы пощупать весь функционал, кроме реальной отправки
писем и сообщений в Telegram — по умолчанию они просто пишутся в лог
backend'а (`EMAIL_ENABLED=false`, `TELEGRAM_ENABLED=false` в `.env`). Как
включить их по-настоящему — см. разделы «Почта» и «Telegram-бот» ниже; оба
варианта работают уже сейчас, без выхода в прод.

Скрипт линуксовый/маковский эквивалент не поставляется — на не-Windows
системах поднимайте backend и frontend вручную (см. ниже) в двух терминалах.

## Backend (FastAPI + Poetry)

```
cd backend
poetry install
copy .env.example .env   # при необходимости поменять секреты/SMTP/Telegram/VK
poetry run alembic upgrade head
poetry run uvicorn app.main:app --reload --port 8000
```

Swagger/OpenAPI: http://127.0.0.1:8000/docs — там же полный список эндпоинтов
с телами запросов/ответов, актуальный всегда (генерируется из кода).

## Frontend (Vue 3 + Vite + Tailwind)

```
cd frontend
npm install
npm run dev      # http://127.0.0.1:5173, проксирует /api и /files на backend:8000
npm run build    # продакшен-сборка в frontend/dist
```

## Оформление: логотип, палитра, анимации

Единый визуальный стиль задаётся в двух местах: `frontend/public/` (файлы логотипа)
и `frontend/src/style.css` (палитра, типографика, переходы). Отдельного UI-фреймворка
нет — только Tailwind v4 и собственные классы.

**Логотип.** Исходник — `public/logo.svg` (вертикальный локап) и `public/logo.png`.
Остальные варианты нарезаны из него:

| Файл | Где используется |
| --- | --- |
| `logo-horizontal.svg` / `logo-horizontal-dark.svg` | шапка сайта (`App.vue`) |
| `logo-mark.svg` / `logo-mark-dark.svg` | подвал, страницы входа/регистрации |
| `favicon.svg` | иконка вкладки (бегун и стрелки на плашке `#E4F7F8`) |
| `logo.png` | `apple-touch-icon` и `og:image` |

Варианты `-dark` отличаются только цветом корпуса ноутбука и шрифта (`#42484e` →
`#e2eaec`): в тёмной теме исходный тёмно-серый сливается с фоном. Переключение —
классами `dark:hidden` / `hidden dark:block`, без JS.

**Палитра** (цвета логотипа) объявлена в блоке `@theme` файла `src/style.css`:

| Цвет | Токен Tailwind | Назначение |
| --- | --- | --- |
| `#0EBCBD` | `brand-500` | основной бирюзовый: кнопки, акценты, активные состояния |
| `#72C4EE` | `aqua-400` | вторичный голубой: рейтинги, вторая стрелка логотипа |
| `#E4F7F8` | `brand-50` | бледно-голубой фон: плашки, чипы, фон страницы |
| `#FBFDFE` | `slate-50` | бледно-серый фон страницы (`--color-paper`) |
| `#50504F` | `slate-600` | основной тёмно-серый: вторичный текст |
| `#090909` | `slate-950` | основной чёрный: текст (`--color-ink`), фон тёмной темы |

Шкала `slate-*` переопределена целиком на фирменные нейтральные серые — почти вся
вёрстка написана на `slate-*`, поэтому цвета всего сайта меняются в одном месте.
Шрифт — Nunito (пакет `@fontsource-variable/nunito`, подключается в `main.ts`,
раздаётся со своего сервера, без обращений к Google Fonts).

Готовые классы для повторяющихся элементов: `.btn-primary`, `.btn-outline`,
`.surface-card`, `.nav-link`, `.back-link`, `.filter-select`.

**Библиотеки UI.** Готовой дизайн-системы нет — вёрстка своя, на Tailwind. Подключены
только headless-примитивы и иконки:

| Пакет | Что даёт | Где |
| --- | --- | --- |
| `reka-ui` | доступные примитивы без своих стилей | календарь записи, меню профиля, модальные окна |
| `lucide-vue-next` | иконки вместо эмодзи и символов | шапка, фильтры, рейтинги, кнопки-крестики |
| `@internationalized/date` | календарные даты без таймзон (нужен `reka-ui`) | `BookingCalendar.vue` |

`components/BookingCalendar.vue` — сетка месяца для выбора даты занятия: свободные дни
(из `GET /tutors/{id}/availability/dates`) кликабельны, занятые приглушены, листание
ограничено диапазоном ответа бэкенда. Используется и в мастере записи
(`BookingWizard.vue`), и в переносе занятия (`RescheduleModal.vue`).

Модальные окна построены на `DialogRoot`/`DialogContent`: фокус запирается внутри окна,
Escape и клик по подложке закрывают его, фокус возвращается на вызвавшую кнопку. Меню
профиля — `DropdownMenuRoot`, с навигацией стрелками. Состояния примитивов стилизуются
через data-атрибуты (`data-[state=open]`, `data-[highlighted]`, `data-[unavailable]`).

**Анимации.** Именованные переходы Vue объявлены глобально в `style.css`, компоненты
подключают их через `<Transition name="...">`:

| Имя | Где |
| --- | --- |
| `fade` | смена страниц (`RouterView`), вкладки кабинета |
| `pop` | меню пользователя в шапке |
| `collapse` | фильтры каталога, «Управление занятием» в карточке занятия (нужна обёртка `.collapse-inner`) |
| `step` | шаги мастера записи |
| `list` | карточки каталога (каскад задаёт переменная `--stagger`) |

Плюс utility-анимации `animate-fade-in`, `animate-fade-in-up`, `animate-pop-in`
(модальные окна, карточки) и плавные ховеры для всех интерактивных элементов из
`@layer base`. Всё движение отключается при системной настройке
`prefers-reduced-motion: reduce`.

## Начальные данные: администратор и справочник предметов

Аккаунт администратора — один на всю систему, создаётся отдельным скриптом
(обычная регистрация формой на сайте создаёт только репетитора/ученика):

```
cd backend
poetry run python -m app.scripts.create_admin --email admin@my-tutor.ru --password ...
```

Повторный запуск с другим email/паролем обновит тот же единственный
администраторский аккаунт, а не создаст второй. Значения можно не передавать
флагами, а прописать `ADMIN_EMAIL`/`ADMIN_PASSWORD` в `.env` — тогда скрипт
подхватит их сам.

Справочник предметов/направлений (раздел 2.1, 4 `project_description.md`)
пустой из коробки — можно наполнить его вручную через админку («Предметы») или
разом накатить стартовый набор (математика, информатика, английский и т.д.,
идемпотентно — повторный запуск ничего не задублирует):

```
poetry run python -m app.scripts.seed_subjects
```

Разослать напоминания о ближайших занятиях (раздел 2.7 `project_description.md`);
нужно запускать по расписанию (cron/systemd timer/Task Scheduler) — планировщик
внутри самого приложения не поднят:

```
poetry run python -m app.scripts.send_reminders
```

## Почта (подтверждение регистрации, сброс пароля)

Писем всего два — подтверждение адреса и сброс пароля; оба транзакционные,
рассылок нет. Шлются они через **собственный SMTP** (Postfix + OpenDKIM на том же
сервере, без сторонних сервисов) — установка и эксплуатация описаны в
[`ops/mail/README.md`](ops/mail/README.md).

**В деве ничего настраивать не нужно.** Пока `EMAIL_ENABLED=false`, письма не
отправляются, а печатаются в лог backend'а целиком — этого достаточно, чтобы
пройти весь флоу руками: берёте ссылку из лога и открываете её.

**Какие письма шлёт сайт:**

| Письмо | Когда | Настраивается |
| --- | --- | --- |
| Подтверждение почты | регистрация, смена адреса, кнопка «отправить ещё раз» | нет, транзакционное |
| Восстановление пароля | запрос сброса | нет, транзакционное |
| Первое занятие с репетитором | первая запись этой пары «ученик — репетитор»: письмо получают **оба** | да, канал уведомлений |
| Напоминание о занятии | за `reminder_lead_minutes` до начала, у каждого своё время | да, канал уведомлений |
| Письмо администратора | вручную из админки, вкладка «Почта» | нет |

«Первое занятие» — именно первая запись в паре (проверка
`booking_service.has_had_booking` до вставки): для репетитора это «пришёл новый
ученик», для ученика — «занятия начались». На повторные записи уходит обычное
короткое уведомление, иначе на каждое занятие в серии сыпалось бы по два письма.
Работает и когда занятие создаёт сам репетитор вручную.

**Канал уведомлений** выбирает пользователь в Настройках: почта и мессенджер /
только почта / только мессенджер / не присылать (`User.notification_channel`,
раньше это была галочка `email_notifications_enabled`). Настройка управляет
уведомлениями и напоминаниями; письма о регистрации и сбросе пароля уходят
всегда — без них аккаунтом нельзя пользоваться. Все уведомления идут через
`notification_service.notify()`, он же уважает выбор канала и пишет результат в
`NotificationLog`.

**Настройки** (`backend/.env`):

```
SMTP_HOST=host.docker.internal   # свой Postfix на хосте; для внешнего провайдера - его хост
SMTP_PORT=25                     # 25 для своего релея, 587 для провайдера
SMTP_USER=                       # пусто: свой Postfix релеит по адресу сети, без SASL
SMTP_PASSWORD=
SMTP_STARTTLS=false              # true для внешнего SMTP на 587
SMTP_FROM=no-reply@my-tutor.ru
MAIL_FROM_NAME=my-tutor.ru
MAIL_REPLY_TO=info@my-tutor.ru   # ответы пользователей, no-reply@ никто не читает
EMAIL_ENABLED=true
FRONTEND_BASE_URL=https://my-tutor.ru   # из него строятся ссылки в письмах
```

Отправка не завязана на конкретную схему: с логином/паролем и STARTTLS тот же код
работает с любым внешним SMTP — меняются только эти переменные.

Что делает код (`app/services/email_service.py`, шаблон —
`app/services/email_templates.py`):

- письмо собирается как `multipart/alternative` — HTML в фирменном стиле сайта
  (бирюзовая кнопка, логотип) плюс обязательная текстовая версия: письмо без
  `text/plain` хуже проходит антиспам-фильтры;
- проставляются `Date`, `Message-ID` на домене отправителя, `Reply-To` и
  `Auto-Submitted: auto-generated` (гасит автоответы «меня нет в офисе»);
- ошибка SMTP не пробрасывается наверх: упавший почтовый сервер не должен
  превращать регистрацию в 500 — неудача пишется в лог, а пользователь может
  нажать «Отправить письмо ещё раз» в Настройках
  (`POST /auth/verify-email/resend`).

**Админка → вкладка «Почта»** (`components/admin/MailTab.vue`) показывает статистику
(отправлено за сутки и за 30 дней, ошибки, входящие, разбивка по типам писем),
журнал всех писем с фильтрами и поиском, и форму «написать письмо» — выбранным
пользователям сайта и/или произвольным адресам. Каждому получателю уходит
отдельное письмо в фирменном оформлении, за раз не больше 50 адресов: это ручная
переписка, а не рассылка. Ответы приходят на `info@my-tutor.ru` и пересылаются
на личный ящик администратора.

Журнал пишется в таблицу `email_log`: исходящие — самим бэкендом при отправке
(включая текст ошибки, если письмо не ушло), входящие — почтовым сервером через
`POST /api/v1/mail/inbound` (см. `ops/mail/README.md`, раздел «Журнал почты в
админке»). Тело письма хранится только превью — журнал нужен для контроля, а не
как почтовый ящик.

Доставляемость обеспечивают DNS-записи (SPF, DKIM, DMARC) и PTR — их список
печатает установщик, см. `ops/mail/README.md`. Без них письма будут попадать в
спам, сколько бы правильных заголовков ни ставил код.

## Telegram-бот

Бот нужен для двух вещей: привязать аккаунт пользователя к его Telegram
(«Подключить Telegram» в Настройках) и после этого слать туда уведомления
(новая запись, отмена/перенос занятия и т.п., раздел 2.7
`project_description.md`).

Бот работает через long polling (сам опрашивает Telegram API), а не через
webhook — специально выбрано так, потому что polling одинаково работает и на
локальной машине, и в проде: не нужен ни публичный домен, ни HTTPS, только
токен бота. Единственное условие — процесс бота должен быть постоянно запущен
(это и есть тот самый шаг, который по-хорошему делается на сервере — см. ниже).

Как настроить и проверить уже сейчас, локально:

1. В Telegram напишите **@BotFather**, команда `/newbot`, следуйте подсказкам —
   получите токен вида `123456:ABC-...` и `@username` бота.
2. Заполните в `backend/.env`:
   ```
   TELEGRAM_BOT_TOKEN=123456:ABC-...
   TELEGRAM_BOT_USERNAME=your_bot_username   # без @
   TELEGRAM_ENABLED=true
   ```
3. Во втором терминале запустите самого бота (отдельный процесс, backend его не
   поднимает сам):
   ```
   cd backend
   poetry run python -m app.scripts.run_telegram_bot
   ```
4. В личном кабинете → «Настройки» нажмите «Подключить Telegram» — откроется
   диалог с ботом по персональной ссылке (`t.me/<bot>?start=<токен>`). Нажмите
   «Запустить» в Telegram, бот подтвердит привязку. Вернитесь на сайт и нажмите
   «Проверить».

Если `TELEGRAM_BOT_USERNAME` не заполнен, кнопка в Настройках честно скажет,
что бот пока не настроен, вместо мёртвой ссылки.

Что по-хорошему делается только при реальном деплое: не сама механика (она уже
работает локально), а её *постоянная доступность* — на сервере скрипт бота
нужно держать под присмотром супервизора, а не в открытом терминале. Для этого
в `docker-compose.yml` есть отдельный сервис `bot` (тот же образ backend'а,
команда заменена на скрипт бота), выключенный по умолчанию через
[profile](https://docs.docker.com/compose/how-tos/profiles/) — чтобы
незаполненный токен не запускал контейнер в бесконечном перезапуске:

```
docker compose --profile bot up -d --build bot
```

Точно так же можно оформить систему напоминаний (`send_reminders.py`) — как
systemd-таймер или cron внутри отдельного контейнера; в `docker-compose.yml`
этого пока нет, добавляется по тому же принципу. Каждый пользователь сам
настраивает, за сколько минут до занятия его предупреждать (Настройки →
«Уведомлять о занятии за … мин», по умолчанию 60) — `send_reminders.py`
проверяет это окно с допуском `tolerance_minutes` (по умолчанию 10 минут в
обе стороны, см. `notification_service.send_upcoming_reminders`), так что
**запускать планировщик нужно не реже, чем раз в 10 минут** — иначе
напоминание может ни разу не попасть в допустимое окно и не отправится
вовсе. Пример systemd-таймера, если бот и backend уже развёрнуты не через
Docker, а напрямую на сервере:

```ini
# /etc/systemd/system/my-tutor-reminders.service
[Unit]
Description=my-tutor.ru lesson reminders

[Service]
Type=oneshot
WorkingDirectory=/opt/my-tutor/backend
ExecStart=/usr/local/bin/poetry run python -m app.scripts.send_reminders
```

```ini
# /etc/systemd/system/my-tutor-reminders.timer
[Unit]
Description=Run my-tutor.ru lesson reminders every 10 minutes

[Timer]
OnCalendar=*:0/10
Persistent=true

[Install]
WantedBy=timers.target
```

```
sudo systemctl enable --now my-tutor-reminders.timer
```

## Вход через VK ID и Яндекс ID

Кроме почты с паролем, в аккаунт можно войти через VK ID или Яндекс ID. К одному
аккаунту можно привязать оба провайдера плюс пароль — список способов входа
показан в Настройках, там же кнопки «Привязать»/«Отвязать». Отвязать последний
оставшийся способ нельзя: иначе в аккаунт стало бы не войти.

Как это работает:

1. Фронтенд просит у бэкенда ссылку авторизации (`POST /auth/oauth/{provider}/start`).
   Бэкенд генерирует одноразовый `state` и PKCE-пару, кладёт их в таблицу
   `oauth_states` (в памяти процесса держать нельзя: колбэк почти наверняка
   попадёт в другой воркер gunicorn) и отдаёт ссылку.
2. Провайдер возвращает пользователя на `/oauth/{provider}/callback`, фронтенд
   пересылает `code`/`state`/`device_id` в `POST /auth/oauth/{provider}/callback`.
   `state` при этом гасится — второй раз тот же код обменять нельзя.
3. Если такой аккаунт провайдера уже привязан — сразу выдаём пару JWT. Если нет —
   отдаём короткоживущий signup-токен, фронтенд показывает короткий шаг регистрации,
   и аккаунт создаётся через `POST /auth/oauth/complete`.

Шаг регистрации спрашивает только то, чего провайдер знать не может: роль
(ученик/репетитор), класс — если ученик, и согласие на обработку ПД. Имя, фамилия и
почта приезжают от провайдера, причём внутри подписанного signup-токена, а не полями
формы — подменить их из браузера нельзя. Почта считается подтверждённой (её проверил
провайдер), письмо со ссылкой не отправляется. Аватар скачивается к нам в
`storage/user-photos/` и становится фото аккаунта (`users.photo_url`); репетитору он
заодно подставляется в анкету как стартовое фото каталога. Если провайдер имени не
отдал (у Яндекса поля профиля бывают пустыми), форма спросит ФИО сама.

Фото аккаунта есть у всех ролей: оно показывается в шапке и в карточке ученика у
репетитора, меняется в Настройках (`POST`/`DELETE /auth/me/photo`, кадрирование тем
же окном, что у репетитора в анкете). У репетитора публичное фото анкеты — отдельная
картинка (`tutor_profiles.photo_url`, вкладка «Профиль»): одно человек ставит для
себя, второе идёт в витрину каталога.

Если почта, которую отдал провайдер, уже занята другим аккаунтом, автоматического
слияния не происходит: пользователю предлагается войти паролем и привязать
провайдера в настройках. Это не UX-каприз, а защита: иначе завести у провайдера
почту с чужим адресом означало бы получить доступ к чужому аккаунту.

**VK ID.** Приложение заводится в кабинете VK ID (vk.com/apps → «Создать
приложение»), нужен только `client_id` — секрет не требуется, VK ID работает по
OAuth 2.1 с PKCE. Прежний протокол `oauth.vk.com` VK отключил 30.09.2025, старые
интеграции с `VK_CLIENT_SECRET` не работают. В настройках приложения пропишите
доверенный redirect URI — ровно тот, что уходит в `VK_REDIRECT_URI` (или
`FRONTEND_BASE_URL` + `/oauth/vk/callback`, если переменная пуста).

**Яндекс ID.** Приложение создаётся на https://oauth.yandex.ru/client/new с
правами `login:email` и `login:info`; оттуда берутся `YANDEX_CLIENT_ID` и
`YANDEX_CLIENT_SECRET`. Redirect URI — `.../oauth/yandex/callback`.

```
VK_CLIENT_ID=51234567
VK_REDIRECT_URI=https://my-tutor.ru/oauth/vk/callback
YANDEX_CLIENT_ID=...
YANDEX_CLIENT_SECRET=...
YANDEX_REDIRECT_URI=https://my-tutor.ru/oauth/yandex/callback
```

Незаполненный провайдер просто не показывается: `GET /auth/oauth/providers`
отдаёт `enabled: false`, и фронтенд не рисует его кнопку. Для локальной разработки
нужен отдельный redirect на `http://localhost:5173/...`, добавленный в настройки
того же приложения (или отдельного тестового).

## Docker / продакшен

```
cd backend && copy .env.example .env   # заполнить JWT_SECRET_KEY и остальные секреты
cd ..
docker compose up --build -d
```

Поднимает два контейнера: `backend` (Gunicorn + Uvicorn-воркеры, применяет
миграции при каждом старте через `docker-entrypoint.sh`) и `nginx` (отдаёт
собранный фронтенд и проксирует `/api`, `/files` на backend). Опциональный
третий — `bot` (см. раздел «Telegram-бот» выше), включается флагом
`--profile bot`. SQLite-файл и загруженные файлы живут на именованном томе
`backend_storage` — переживают `docker compose up --build`. Порт 80
публикуется наружу.

**Пошагово, с нуля, на чистом Linux-сервере:**

1. Поставьте Docker и Docker Compose plugin (`docker compose version` должен
   отработать без ошибок).
2. Склонируйте репозиторий на сервер: `git clone <repo> my-tutor && cd my-tutor`.
3. `cd backend && cp .env.example .env`, заполните как минимум
   `JWT_SECRET_KEY` (длинная случайная строка — например,
   `openssl rand -hex 32`) и `FRONTEND_BASE_URL` (реальный домен, например
   `https://my-tutor.ru`); остальное — по разделам «Почта»/«Telegram-бот»
   выше, можно и позже. `cd ..`.
4. `docker compose up --build -d` — соберёт образы и поднимет `backend` +
   `nginx`.
5. Направьте DNS домена на IP сервера, поставьте перед nginx TLS-терминацию
   (см. ниже) — без неё пароли и токены идут в открытом виде по HTTP.
6. Создайте администратора и (по желанию) справочник предметов — те же
   команды, что и локально, но через `docker compose exec`:
   ```
   docker compose exec backend poetry run python -m app.scripts.create_admin --email admin@my-tutor.ru --password ...
   docker compose exec backend poetry run python -m app.scripts.seed_subjects
   ```
7. Проверьте: `docker compose ps` (оба контейнера в статусе `running`; отдельных
   healthcheck'ов в compose-файле нет), `curl http://127.0.0.1/api/v1/health` →
   `{"status":"ok"}`.

**TLS/HTTPS.** В комплекте не настроена — контейнер `nginx` слушает голый
HTTP на 80 порту. Проще всего добавить терминацию TLS перед ним, не трогая
`docker-compose.yml` этого репозитория:
- Отдельный [Caddy](https://caddyserver.com/) или
  [Traefik](https://traefik.io/) контейнер перед `nginx`, который сам
  выпускает и продлевает сертификат Let's Encrypt по домену.
- Либо `certbot` прямо на хосте (вне Docker) + системный nginx/haproxy как
  внешний реверс-прокси перед портом 80 контейнера.

**Рабочий процесс: тестируем локально, выкатываем на сервер, не ломая прод.**

Проект ещё активно меняется, поэтому `main` — это ветка, из которой
деплоят, а не черновик. Порядок для новой фичи/правки:

1. Отдельная ветка от `main`, разработка и ручная проверка локально через
   `run-local.ps1` (раздел «Быстрый локальный запуск») — там своя SQLite-база
   (`backend/storage/db.sqlite3`), никак не пересекающаяся с продакшеном.
2. PR в `main` — CI (`.github/workflows/ci.yml`) прогоняет линтеры, тесты и
   сборку обоих частей на каждый push в PR (раздел «Тесты, линтеры, CI»).
   Мержим только когда CI зелёный.
3. На сервере — сначала бэкап (см. ниже), затем обновление (команды ниже).
4. После деплоя — быстрый смоук-тест: `curl http://127.0.0.1/api/v1/health`
   и открыть сайт в браузере, проверить логи (`docker compose logs -f
   backend`) на ошибки при старте.
5. Если релиз значимый — тег на смёрженном коммите (`git tag vX.Y.Z && git
   push --tags`), как уже сделано для `v0.1.0`…`v0.4.0`. Тег — это точка
   отката: если после деплоя что-то пошло не так, можно быстро вернуться к
   предыдущей рабочей версии.

**Обновление после изменений в коде:**

```
git pull
docker compose up --build -d
```

Пересоберёт изменившиеся образы, применит новые миграции (entrypoint
backend'а делает это на каждом старте) и перезапустит контейнеры с
downtime в несколько секунд.

**Откат к предыдущей версии**, если после деплоя что-то сломалось:

```
git checkout vX.Y.Z   # предыдущий рабочий тег
docker compose up --build -d
```

Это откатывает код и статику, но **не откатывает саму базу** — Alembic
накатывает миграции вперёд, а не назад. Пока миграции только добавляют
таблицы/колонки (как сейчас), старый код на новой схеме работает нормально
(просто не знает о новых колонках), так что этого отката достаточно. Если
случится миграция, которая физически удаляет или переименовывает
данные, — заранее продумайте её обратимость (`downgrade()` в самой
миграции) или восстанавливайтесь из бэкапа тома, снятого перед деплоем
(ниже).

**Бэкап.** Всё, что нужно сохранить — именованный том `backend_storage`
(SQLite-файл `db.sqlite3` + все загруженные фото/файлы):

```
docker run --rm -v my-tutor_backend_storage:/data -v $(pwd):/backup alpine \
  tar czf /backup/my-tutor-backup-$(date +%F).tar.gz -C /data .
```

(имя тома может отличаться в зависимости от имени папки проекта — уточните
через `docker volume ls`).

**Логи:** `docker compose logs -f backend` / `docker compose logs -f nginx`.
Backend логирует одним JSON-объектом на строку вне режима отладки
(`DEBUG=false`) — удобно скармливать любому агрегатору логов без
допарсинга.

**Миграция с SQLite на PostgreSQL** (раздел 9 `project_description.md`) —
поднять Postgres (отдельным сервисом в `docker-compose.yml` или managed
БД), сменить `DATABASE_URL` в конфиге `backend`-сервиса на
`postgresql+asyncpg://user:pass@host/dbname` (убрав override SQLite-пути) и
перезапустить — миграции Alembic отработают на новой БД так же, как на
SQLite, схема не отличается.

## Переменные окружения

Все — в `backend/.env` (шаблон в `backend/.env.example`).

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ENVIRONMENT` | `development` | произвольная метка окружения (попадает в Sentry, если подключён) |
| `DEBUG` | `true` | человекочитаемые логи и подробные ошибки; `false` в проде включает JSON-логи |
| `DATABASE_URL` | локальный SQLite-файл | строка подключения к БД (SQLite или `postgresql+asyncpg://...`) |
| `JWT_SECRET_KEY` | небезопасный дефолт | **обязательно сменить в проде** — секрет для подписи JWT; backend откажется стартовать с дефолтом при `DEBUG=false` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | срок жизни access-токена |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `30` | срок жизни refresh-токена |
| `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM` | пусто | куда и от кого слать письма, см. раздел «Почта» |
| `SMTP_STARTTLS` | `true` | STARTTLS на отправке; `false` для своего Postfix на 25 порту |
| `SMTP_TIMEOUT_SECONDS` | `20` | таймаут SMTP-сессии |
| `MAIL_FROM_NAME` | `my-tutor.ru` | отображаемое имя в поле «От кого» |
| `MAIL_REPLY_TO` | пусто | адрес для ответов пользователей (`Reply-To`) |
| `MAIL_INGEST_TOKEN` | пусто | секрет для `POST /mail/inbound` — приём входящих писем в журнал; пусто = ручка выключена |
| `EMAIL_ENABLED` | `false` | `true` — реально слать письма; `false` — только логировать |
| `TELEGRAM_BOT_TOKEN` | пусто | токен бота от @BotFather, см. раздел «Telegram-бот» |
| `TELEGRAM_ENABLED` | `false` | `true` — включить Telegram-канал уведомлений |
| `TELEGRAM_BOT_USERNAME` | пусто | `@username` бота без `@`, для диплинка «Подключить Telegram» |
| `VK_CLIENT_ID`/`VK_REDIRECT_URI` | пусто | креды VK ID-приложения для входа через VK. Секрет не нужен: VK ID работает по OAuth 2.1 с PKCE. Пустой `REDIRECT_URI` = `FRONTEND_BASE_URL` + `/oauth/vk/callback` |
| `YANDEX_CLIENT_ID`/`YANDEX_CLIENT_SECRET`/`YANDEX_REDIRECT_URI` | пусто | креды приложения Яндекс ID (права `login:email`, `login:info`) для входа через Яндекс |
| `FRONTEND_BASE_URL` | `http://localhost:5173` | домен фронтенда — используется в ссылках в письмах |
| `CORS_ORIGINS` | `["http://localhost:5173"]` | **обязательно сменить в проде** — список разрешённых origin для CORS (JSON-массив); с дефолтом фронтенд с реального домена не сможет достучаться до API |
| `ADMIN_EMAIL`/`ADMIN_PASSWORD` | пусто | подхватываются `create_admin.py`, если не передать флагами |
| `RATE_LIMIT_ENABLED` | `true` | лимит запросов на `/auth/*` по IP; выключается только тестами |
| `SENTRY_DSN` | пусто | если задан — ошибки летят в Sentry; пусто = функциональность полностью выключена |

## Что умеет сайт (кратко)

Полное описание по ролям — в [`project_description.md`](./project_description.md).
Здесь — конспект.

**Репетитор:** анкета с фото, форматированным «о себе» (включая вставку
картинок с выравниванием) и красивой ссылкой на профиль (свой ник вместо

слотов, перерывом между занятиями, минимальным запасом времени; полный CRUD
по записям, ручные брони, еженедельная регулярность, отмена/перенос без
ограничений (в отличие от ученика); отдельные политики отмены/переноса для
учеников; домашние задания с ручным контролем статуса, отправкой сразу
нескольким ученикам/группам, копированием и фильтрами по ученику/статусу/дате;
личный и групповой чат; журнал событий с фильтрами; группы подготовки
(заявки, зачисление, посещаемость по каждому ученику, перенос отдельного
занятия группы); уведомления в Telegram/на почту/внутри сайта («Системные
уведомления» в чате) с настраиваемым временем напоминания о занятии.

**Ученик:** главная страница-лендинг (что за платформа, плитки предметов с
числом репетиторов, «как это работает», обзор возможностей, свежие статьи
блога, FAQ с `FAQPage`-разметкой для поисковиков); блог со списком статей
(`/blog`) и отдельной страницей каждой статьи (`/blog/<slug>`, `Article`-разметка);
публичный каталог с фильтром по
предмету/цене, скрываемыми фильтрами, подгрузкой по скроллу и
наведением-увеличением карточек; мастер
записи (тип занятия → дата → время → подтверждение, время — в своём поясе
плюс МСК); групповые занятия видны в общем списке «Занятия» вместе с
индивидуальными, с отдельной карточкой (без переноса — переносить может
только репетитор — и с уведомлением репетитора о неявке при отмене);
отмена/перенос индивидуальных занятий в рамках политики репетитора;
регулярная запись; заявки в группы; домашние задания (файл или отметка);
чат; статистика с журналом событий; отзывы репетиторам.

**Администратор:** полный CRUD по репетиторам (включая анкету целиком, не
только базовые поля) и ученикам; список занятий по всей платформе с
фильтрами (репетитор/предмет/направление/класс/период) и переносом через тот
же мастер, что у репетитора; управление группами вплоть до передачи другому
репетитору; CRUD справочника предметов/направлений; блог — единственный, кто пишет
статьи: тот же редактор форматированного текста, что у репетитора в «о себе»
(ссылки, картинки с выравниванием), обложка, черновики и публикация в один
клик, адрес статьи собирается транслитерацией заголовка; редактирование текстов
системных уведомлений отдельно для каждого события и роли получателя.

**Общее:** JWT-авторизация с автообновлением токена, вход по email+паролю,
через VK ID или Яндекс ID (несколько способов входа на один аккаунт,
привязка/отвязка в настройках), подтверждение email, восстановление пароля, привязка Telegram с
настраиваемым временем напоминания о занятии, rate limiting и временная
блокировка аккаунта при подборе пароля, счётчик непрочитанных
сообщений/уведомлений в шапке и в кабинете, светлая/тёмная тема, адаптивная
вёрстка, правовые страницы (152-ФЗ).

## Известные ограничения

В форме ручной записи на занятие («Резерв / запись вручную» у репетитора и в
админке) ученик всё ещё указывается по ID — поиск по имени сделан только для
формы выдачи домашнего задания. Календарного виджета нет, списки простые.
Дизайн утилитарный (Tailwind без кастомной темы). Telegram-бот и почта
требуют ручной настройки токена/SMTP-кредов (см. разделы выше) — без них всё
работает, но уведомления только логируются. TLS/HTTPS не настроен из коробки
— добавляется отдельно перед выходом в прод (см. «Docker / продакшен»).
`mypy` в CI не блокирует сборку — есть накопленный технический долг по
типизации, задача на будущее. Фронтенд — SPA без SSR: `<title>`, description
и JSON-LD проставляются из компонентов (`utils/pageMeta.ts`), поэтому статьи
блога и анкеты репетиторов индексируются только теми поисковиками, которые
исполняют JS. Для надёжной выдачи нужен пререндер на сборке — отдельная
задача.
